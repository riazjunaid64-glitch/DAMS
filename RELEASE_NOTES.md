# Unreleased

## Manage accounts and the go-live date (KAN-91)

Manage accounts is rebuilt on the shared components for desktop and phone: one header, seven groups (Cash & bank, Cash held by staff, Fixed assets, Work in progress, Receivables, Liabilities, Capital) each with a subtotal row, no stat boxes and no "All accounts total", filters for search, Type, Holder and Status, and a pencil and a ⋯ menu on each row (an active system account has the pencil only). Clicking a row opens Account details with the figures, the tax held for FBR, and the transactions with a running balance. Add and Edit have no Display order (Edit sends the saved one back). Deactivate and Reactivate ask in a popup, and a refusal shows as a toast instead of a browser alert. A red notice shows the difference when the opening debits and credits do not match.

**The opening balance is typed once, in Add / Edit account**, on the account's own side (a minus sign means the other side), at any time, also after go-live. Changing it, or typing a non-zero one on a new account once a go-live date is saved, asks "Change the opening balance?" first, and every change writes a history row (who, from, to). Customer deposits, Customer receivables and Commission payable take no typed opening: the server refuses a new figure ("... is worked out from bookings and commissions ...") and accepts a legacy one saved unchanged. Loan accounts still cannot open below zero. A non-zero opening now counts as history, so such an account cannot change type or be deleted.

**The go-live date is a plain setting** in Finance settings > Financial year (shared date picker, not after today). Everything that read the date of the committed opening balance set now reads it through `FinanceDateRules.BaselineAsync`, so no report or posting-date check changes. A saved date cannot be emptied; moving it asks first, and the server refuses a later date while any record is dated before it (it names the records and the earliest day). The posting message is now "... cannot be before the go-live date (dd MMM yyyy). Everything up to that date is already inside the opening balances." The **Opening balances tab is gone** from Finance settings, and so are its panel, the `OpeningBalanceService`, the `api/finance/opening-balances` endpoints (`GET current`, `POST`, `PUT {id}`, `POST {id}/commit`, `POST {id}/reopen`), their DTOs and entities. The partner statement's go-live row now says "Opening balance".

API: `FinanceSettingsDto` and `SaveFinanceSettingsDto` carry `goLiveDate` (null on save = unchanged). `FinanceAccountsOverviewDto` carries `openingDebitTotal`, `openingCreditTotal`, `goLiveDate` and `holderNames` (every account's holder, distinct and sorted). `FinanceAccount` and `FinanceSetting` are now in the correction trail (`FinanceRecordAudits`), which records the opening balance and the go-live date; `UpdatedAt` is left out, so saving identical values writes nothing.

Deploying this runs the `MoveGoLiveDateToFinanceSettings` migration, **one-way**. It adds `FinanceSettings.GoLiveDate` and fills it with the date of the committed opening balance set (none when no set was committed, so there are still no date limits). It copies the old audit lines (`OpeningBalanceSet`) and every per-account note or amount (`FinanceAccount`, action `OpeningNote`) into `FinanceRecordAudits`, then drops `OpeningBalanceAuditEntries`, `OpeningBalanceEntries` and `OpeningBalanceSets`. `Down` recreates the three tables empty. A set that was reopened keeps its date, and amounts edited in it but never recommitted are not applied (they survive only as history rows); a draft that was never committed leaves the go-live date empty and its amounts survive only as history rows.

**Before deploying:** back up, then run `SELECT [Id],[AsAtDate],[IsCommitted],[CommittedAt],(SELECT COUNT(*) FROM [OpeningBalanceEntries] e WHERE e.[OpeningBalanceSetId]=s.[Id]) AS Entries FROM [OpeningBalanceSets] s;` and, for a reopened set, `SELECT a.[Name], a.[OpeningBalance], e.[DebitAmount], e.[CreditAmount] FROM [OpeningBalanceEntries] e JOIN [FinanceAccounts] a ON a.[Id]=e.[FinanceAccountId];` to see whether any draft amount differs from the account. Re-type any wanted figure in Manage accounts after the deploy. After it, compare `/api/Finance/balance-sheet` and `/trial-balance` totals with the figures from before.

## Customer review fixes (KAN-79, KAN-80)

On a phone the customer page header card now starts with the Back button, as the ticket says. Creating a customer is one serializable unit (duplicate check and insert), so two requests with the same phone or CNIC can no longer both succeed; the loser gets the usual 409. The customer list now counts, filters and pages in SQL and reads only the requested page. `POST /api/Customer` no longer takes `source`: every customer created there is a walk-in.

## Customer page: Documents tab (KAN-82)

The Documents tab has only three statuses: **Needed**, **Uploaded** and **Not needed**; every review step is gone. It lists **Still needed** (documents asked from this customer with no file yet) and **Done** (uploaded or not needed), one action set per row: Needed has **Not needed** and **Upload**, Uploaded has **View**, Not needed has **Upload**. Upload opens the file picker at once and the document is Uploaded as soon as the file arrives. A row shows "Uploading · 60%", a thin bar and a × to stop; a wrong file type or a file over 10 MB is stopped in the browser with a red message on the row. One rule for every document: **PDF, JPG or PNG, up to 10 MB**. **Not needed** always asks for a reason and moves the document to Done. **View** shows the file inside the popup, with **Replace file** (the old file stays under **Older files**) and **Download**; viewing and downloading are both recorded. **Add document** (extra documents) lists the types that are not asked from every customer and not already on this customer, plus **Other** with a Name box, and saves the document already Uploaded.

Shared pieces: the Attach proof field takes a file rule and a required mark (customer documents use it), plus a Download icon. The Document setup page no longer has per-type file types, size or due days.

Server: `CustomerDocumentStatus` is now `Needed`, `Uploaded`, `NotNeeded`. The `CustomerDocumentsThreeStatuses` migration remaps every existing requirement in one statement (Missing, Requested, Rejected, Replacement required, Postponed and Expired become Needed; Received, Under review and Approved become Uploaded; Waived and Not applicable become Not needed, with the reason, person and day copied from their latest Waived / Not applicable audit row), adds the not-needed reason, person and time, and **drops** the due date, the per-requirement and per-category file types and size, the category default due days and the file review columns (review reason, status, person and time). The audit rows keep their action and notes, and their old status numbers are moved to the new meaning with the same mapping, so no old number reads as a different new status. `GET /api/customer-documents/customers/{id}` now answers `stillNeeded`, `done`, the visible `requirements` (asked from the customer, with a file, or not needed) and `availableTypes`, and no longer carries `summary`. New calls: `POST .../customers/{id}/documents` (add a document with its first file; an existing quiet row of that type is reused, one the customer can already see is a 409), `POST .../requirements/{id}/not-needed` (reason required, only from Needed), `GET .../versions/{id}/view` (private file, no-store, nosniff, recorded as FileViewed). `POST .../upload` now replaces the current file (the old one is kept as an older file) and always leaves the document Uploaded. Removed: `POST .../requirements`, `POST .../status` and `PUT .../due-date`. The Add document popup offers every active type that is not both required and handed to every new customer (and not already on the customer). The "documents needed" number on the customer list and page is the count of required documents with status Needed.

## Customer page: Bookings tab (KAN-81)

The Bookings tab on the customer page shows one card per booking, newest first: the booking number and status badge (the Bookings list names and colours), "Unit B08 · Floria Heights", the booked date, and three figures — **Net price**, **Paid** (green, the booking page's Collected) and **Still due** (its Outstanding, "—" once the booking is cancelled). The whole card opens the booking, and desktop also has a Details button. With no bookings the tab shows "No bookings yet" and the tab count is hidden.

`GET /api/Booking/customer/{id}` now answers `{ items }` of slim rows (`id`, `bookingReference`, `status`, `unitNumber`, `projectName`, `bookingDate`, `netPrice`, `collected`, `outstanding`) built with the same figure function as the booking page, so the numbers cannot differ. It no longer stops at 100 bookings: every booking of the customer is returned, and the count on the customer detail is the length of this list. No migration.

## Customer page, Edit, Block and Unblock (KAN-80)

The customer page has one header (name, a badge reading "N documents needed", "Documents complete" or red "Blocked", the phone, CNIC and "Customer since"), three tabs (Overview, Bookings with its count, Documents) and an Overview of Personal details, Contact and Notes cards; anything never filled in reads "Not added" and a blank WhatsApp reads "Same as mobile". The History tab is gone. **Edit** is now the shared Customer form (with Notes; no Status or Source) and saves date of birth, nationality, occupation and WhatsApp, which could never be changed before. **Block** asks for a required reason, stops new bookings, and shows a red "New bookings are stopped" notice with the reason, the person and the day; **Unblock** asks first and reverses it. **New booking** opens New booking with this customer chosen, and is not offered for a blocked customer (the server still refuses them). On a phone the header has New booking and ⋯ (Edit details, Block customer); a blocked customer has Unblock and the Edit pencil.

New shared pieces: Block and ID-card icons, a content area on the confirm box (for the Reason field; KAN-82 reuses it), and a text badge plus a details row on the page header.

Server: a customer is now only Active or Blocked, and **every Inactive customer becomes Active** when the `CustomerBlockReasonAndStatusLog` migration runs. `POST /api/Customer/{id}/block` (reason required) stores the reason, who and when on the customer; `POST /api/Customer/{id}/unblock` clears them. Each block and unblock writes one row to the new append-only `CustomerStatusLogs` table (audit only, no screen yet). The customer response now carries date of birth, nationality, occupation, WhatsApp, the blocked reason / person / time and `documentsNeeded`, and no longer carries `documentSummary`. `PUT /api/Customer/{id}` accepts the date of birth, nationality, occupation and WhatsApp, no longer accepts `status`, and refuses a mobile or CNIC (digits only) that belongs to another customer with the same 409 answer as New customer. The documents checklist no longer returns the change list (`history`, `hasMoreHistory`); the paged history call remains for the audit trail.

## Booking page: Installment plan and Payments tabs (KAN-74)

The Installment plan tab is rebuilt on the shared components for desktop and phone. With no plan it shows one card, "No installment plan yet", with what is to be scheduled and a **Create plan** button; the plan form is now a popup (full screen on a phone) with Agreed sale price, Discount %, Installments, Frequency, **First due**, and an optional Possession amount and Possession due, and a strip showing what is to be scheduled and what each installment will be. **Change plan** opens the same popup filled from the current plan and replaces every installment; it shows only while the server says the plan can still be replaced. A plan shows Plan total, Paid, Remaining and Overdue (Plan total, Paid and Next due while nothing is paid), overdue due dates in red, and a **Record payment** button on every unpaid row, the possession row included. Long plans page at 20 rows on desktop; a phone shows the last two paid and the next unpaid installments with **Show all**. An orange notice with a Change plan button replaces the payment buttons whenever money is outside the plan.

The Payments tab shows Collected, Rebate credits and Outstanding and a payment history (receipt, date, what it was for, method, reference, amount) with each payment's proof or **Attach proof**, and a Receipt button that opens the receipt page inside the app.

Server changes: the date entered for the plan is now the due date of **installment 1** (it used to become one period later, so "Oct 26" was Nov 26); later installments are counted from that date, so a 31st does not drift to the 28th after February. The schedule returns its settings (installments, frequency, first due, possession amount and due date), where first due is read off the plan itself, so plans built before this change open Change plan on the right date. `unscheduledBalance` is now reported whenever what is left to pay is more than the unpaid installments hold, whatever the cause (it used to be only after a reversed rebate credit), and installment payments are refused while it is above 0 with "Change the plan for the current balance first." A plan that was built by hand or imported short of the balance is therefore also held until it is changed. Each payment row now carries `installmentSequence`, `installmentType`, `financeAccountId`, `accountName` and `recordedByName`, and the list is newest first. `POST /api/Booking/{id}/installment-plan/generate` takes an `Idempotency-Key` header like payments, so a double click never builds two plans, and building a plan is also safe against the database's own retry: a first plan whose commit was replayed reports the plan it built instead of failing with "already exists". `frequency` and `installmentStartDate` are now genuinely required on that call (they used to fall back to Monthly and year 1 when left out), and an unknown frequency is refused. Deploying this runs the `AddInstallmentPlanAttempts` migration: one new append-only table holding the unique key of each create / change plan attempt (nothing backfilled), so a replayed old attempt can never overwrite a newer plan.

**Before deploying:** because payments are now refused while money is outside the plan, a booking whose plan is short of the balance **and** already has an installment payment can be neither paid nor changed (a plan with payments cannot be replaced). Find them first and repair them by hand: a booking with installments where net price − payments − non-cash credits is more than what its unpaid installments hold, and at least one installment payment exists.

## Booking page: header, Summary and status actions (KAN-73)

The booking page has a new header with one main button for the current status (Record payment, Give possession or Complete sale), Print application form, and Cancel booking where the server allows it; on a phone it shows the main button plus ⋯, or a printer icon when Print is all that is left. The Summary tab is rebuilt for Payment plan, Awaiting booking amount, Terms not set and Possession given, and a tab's data is read only when the tab is first opened. Set terms, Edit terms, Record booking amount, Record payment, Give possession and Complete sale are popups; Complete sale stays disabled while anything is owed. The installment payment popup opens from the existing installment rows, and the Installment plan, Payments and Commission & rebate tab contents are unchanged until their own tickets.

The booking response now carries `collected`, `outstanding`, `installmentsPaid`, `installmentsTotal`, `nextInstallment` (what is left on the earliest unpaid installment, its due date and whether it is overdue) and, for a converted booking, `convertedFromLead` (never sent to the customer's own view). Every Set / Edit terms, and every change of price or discount through the installment plan, saves a row in the new `BookingTermsHistories` table (audit only, no screen yet). The due-by date must be today or later, and a discount reason that is not sent is kept instead of wiped. A payment must name its method (it used to become Cash silently) and needs a reference unless it is Cash. Terms, possession and complete-sale now take an `Idempotency-Key` like payments, and someone who loses a race gets "This booking was just changed by someone else. Refresh and try again." instead of a server error.

Recording a payment now answers with the exact `recordedPaymentId` it created, and the proof file is attached to that payment; if the upload fails the popup closes with a warning and the file is attached later from the saved payment. The Attach proof field is also on both refund popups (pay now at cancellation, and pay a pending refund later). Saved payments (Payment History) and saved refunds now show the proof file name, which opens the file, or an **Attach proof** link when there is none, so a failed upload can always be sent again from the saved record. The salary slip's editable Pay Date no longer carries a native date type. The terms history is append-only and only written when a term actually changed. The Bookings list shows the amount still due from the server, so a rebate credit no longer looks like money owed.

Deploying this runs the `AddBookingTermsHistory` migration: one new table, nothing backfilled. Any client calling `PUT /api/Booking/{id}/financials`, `POST .../possession` or `POST .../complete` must now send an `Idempotency-Key` header, and payment calls must send `paymentMethod` (and `paymentReference` for non-cash methods).

## Bookings list redesign and Requests removed (KAN-72)

The Bookings list is rebuilt on the shared components for desktop and phone: summary cards that filter (Total includes cancelled bookings; there is no Cancelled card), a Status and Project filter, 20 per page with "Showing 1–20 of 46 bookings", and Load more on phone. The counts come from a new `GET /api/Booking/summary` call that follows the search and project filters but not the status filter. Bookings search now finds a customer by any phone format (`0300-1234567`, `0300 1234567`, `03001234567`, `+92 300 1234567`) and by CNIC with or without dashes. Booking, installment, commission, rebate and refund status names and colours come from one module (`features/bookings/statusNames.ts`) and the shared status badge.

The website booking Requests pages are removed for every role, along with the request cards, "Withdraw request" and the "Under review" count in the client portal. `/bookings` and old notification links now open the Bookings list. `POST /api/BookingRequest` now answers "Booking requests are closed. Please contact our sales team." Old request data, and the links from old bookings and leads to it, are untouched, and Lead Convert works as before. No migration.

## Shared date and time pickers (KAN-70)

Every built-in date, time and date-time input in the app is replaced by one shared date picker and one shared time picker. Dates show as "Sep 29, 2026" and times as "11:30 AM" on desktop and phone; forms still send `YYYY-MM-DD` and `HH:mm`, so no server change is needed. "Today" is today in Pakistan. Payment, refund, date-of-birth and other finance dates cannot be picked in the future, and the cancellation refund date is locked to today, which is the only date the server accepts for it. The notification admin's send time now uses the date and time pair. The salary month selector is unchanged.

## Proof on customer payments and refunds (KAN-71)

A shared **Attach proof** upload field (one file, PDF, image, Word or Excel, up to 15 MB, checked in the browser first) is added to the component library. The server now accepts one proof file for each customer payment and each cancellation refund, using the same private storage, file checks, Admin and Accountant access and audit rows as commission and rebate proof (`POST /api/finance/commissions-rebates/evidence/CustomerPayment/{id}` and `.../CancellationRefund/{id}`). The booking detail returns `proof` (id, file name, size) on each payment and on the refund; a customer's own view of a booking never includes it.

Deploying this runs the `AddPaymentAndRefundProof` migration: two nullable columns on `FinancialEvidence`, unique filtered indexes (one file per payment or refund), and a wider "exactly one owner" check constraint. Nothing is backfilled.

## Site visit reminders (KAN-30)

Site visit reminders now follow the admin notification rule, using Pakistan calendar days. Visits without a custom reminder are announced on the configured number of days before the visit (one day by default); setting lead days to zero disables that advance reminder. A visit's own reminder time replaces the admin advance timing. The separate visit-day reminder runs only when **Remind on due date** is enabled. Turning off the Site visit reminder rule stops both reminders, while missed-visit marking and escalation continue.

Existing scheduled visits within the advance window may receive a reminder on the first scan after this release. Rescheduled visits can receive reminders again for their new schedule.
